3 ý quan trọng nhất:
  1. Bạn tạo nhánh, bạn commit, bạn push. AI chỉ kiểm tra nhánh đúng gốc và không bao giờ git push trên dự án.
  2. AI không chạy SQL ghi. Bạn tự chạy script trên DB Dev để test, rồi tự chạy trên Prod.
  3. Kích cỡ task (-s/-m/-l) chỉ quyết định lượng giấy tờ, không nới bất kỳ luật an toàn nào.

4. Cú pháp lên plan: kích cỡ, version, super plan

Lên plan <TASK_ID> [-s|-m|-l] [-v2|-v3] [+super]: <mô tả>
CờÝ nghĩa
-sNhỏ: sửa thẳng 1 vài chức năng đã có ("sửa A, sửa B"). Plan rút gọn, không HTML, Tester soi diff + test nhanh.
-mVừa: cụm nhiều chức năng / chức năng mới trong 1 module/màn hình. Plan đầy đủ, Tester đủ 5 cổng.
-lLớn: nhiều module/màn hình, luồng liên hoàn, tích hợp ngoài. Plan chia giai đoạn, có HTML, Tester bắt buộc khác model Coder.
-v2 / -v3Chỉ làm 1 version. Không ghi = làm cả v2 + v3.
+superPlanner viết sẵn bản vá (đoạn code gốc + đoạn code mới) cho mọi bước → Coder chỉ tìm và thay. Dùng khi Coder là model nhanh/yếu.

Cờ kích cỡ do bạn quyết định. Quên gắn → Planner đề xuất 1 mức và hỏi. Planner không bao giờ tự đổi cờ.

Chuông báo (chỉ với -s)

Task gắn -s mà có 1 trong các dấu hiệu dưới → Planner dừng hỏi: giữ -s (chỉ thêm phần an toàn bắt buộc) hay nâng -m.

  1. Đụng STO / View / Function / bảng / cột (giữ -s vẫn bắt buộc snapshot v2/v3 + script tách riêng).
  2. Đụng tiền, BHYT, cổng thông tin, API đối tác.
  3. Phải xóa code / logic có sẵn.
  4. Sửa > 3 file, hoặc v2 và v3 khác nhau đúng chỗ cần sửa.

Khi nào dùng super plan

CoderTaskDùng
Mạnh (chậm cũng được)Bình thườngPlan thường (không cờ)
Yếu / nhanh (vd SWE 2 flash)Bất kỳ+super
MạnhCó bước rủi ro caoPlan thường — Planner tự đánh dấu [super] cho bước sửa sto, map mã gửi cổng/đối tác, logic tiền
Super plan làm Planner chậm hơn và plan dài hơn. Coder mạnh + +super không tốt hơn bao nhiêu mà còn bị trói tay. Dùng super plan thì Tester bắt buộc khác model Coder.

Ví dụ

Lên plan HIS-1234 -s -v3: sửa chức năng A, B ở màn Tiếp nhận
Lên plan HIS-1240 -m: bổ sung chức năng xuất Excel danh sách thu tiền
Lên plan HIS-1240 -m +super: bổ sung chức năng xuất Excel danh sách thu tiền
Lên plan HIS-1250 -l -v2: tích hợp cổng BHYT mới

6. Task nhỏ (-s) và task lớn (-l)

Task nhỏ -s

Dùng skill plan-task: Lên plan HIS-1234 -s -v3: sửa label nút Lưu và căn lại cột Ngày ở màn Tiếp nhận

11. Luật bắt buộc & việc AI không bao giờ làm

6 luật Zero-Tolerance (vi phạm = FAIL ngay)

#LuậtNghĩa là
1Không làm mất code đồng nghiệpChỉ sửa đúng chỗ trong plan; không viết lại cả file; không "dọn dẹp" hay refactor ngoài plan. Tester đọc 100% dòng bị xóa.
2Không đoánKhông bịa tên cột, id/name HTML, tham số sto. Lệch tên → dừng hỏi.
3Không silent fallbackCấm data.ColA ?? data.colA ?? "". Mỗi trường đúng 1 tên đã kiểm chứng.
4Fail-FastNhánh else/default khi map mã/trạng thái phải báo lỗi, không gán mã mặc định.
5Bảo mật cấu hình & chỉ đọc DBKhông đọc appsettings*/Web.config/.env khi chưa được phép; được phép cũng chỉ SELECT.
6An toàn GitAI không git push trên dự án; không sửa trên master_2 / master_3; không tự tạo/đổi nhánh — chỉ kiểm tra nhánh bạn tạo.

Luật SQL

  • Sửa sto chạy cả 2 version → bắt buộc có đủ before_v2.sql và before_v3.sql (lấy từ Prod).
  • Script luôn tách riêng v2 / v3; thứ tự Table → Index → Func/View → Sto → Seed; có 99_rollback cho cột/index/seed/sto mới.
  • Cột mới phải NULL hoặc có DEFAULT; chạy SQL trên Prod xong mới deploy code.
  • Chỉ cú pháp SQL Server 2017 (không GREATEST, LEAST, GENERATE_SERIES).

AI không bao giờ

  • Chạy dotnet build / dotnet run (bạn dùng dotnet watch run).
  • Chạy SQL ghi / EXEC sto / ALTER lên bất kỳ DB nào.
  • Tự ghi vào kho kiến thức chính thức (chỉ tạo nháp; ngoại lệ: thêm dòng lịch sử dùng/chạy).
  • Lưu mật khẩu, connection string, dữ liệu bệnh nhân thật vào kho hay kịch bản.
